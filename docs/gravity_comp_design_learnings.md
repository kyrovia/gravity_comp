# gravity_comp 设计学习记录

写`gravity_comp` 源码时的个人学习笔记：如何划分抽象、Pimpl 编译防火墙、以及 `inline` 的真实含义。

## 如何寻找抽象边界

先完成核心数据流，再沿数据流寻找候选边界：

```text
模型文件 → 动力学模型 → g(q) → 控制律 → τ → 仿真或真机
```

如果下游只需要上游的结果，不需要了解其计算过程，这个结果就是良好的隔离点。

决定哪些内容属于同一抽象时，依次判断：

1. 是否承担同一职责；
2. 是否维护同一状态或不变量；
3. 是否因为同一种原因一起变化；
4. 是否依赖同一组领域知识。

共同依赖某个库只是辅助信号，不是充分条件。抽象应随真实需求迭代产生，不要提前为尚未出现的变化设计复杂框架。

在本项目中：

- `PinModel` 负责模型加载和动力学计算，维护匹配的 Pinocchio `Model/Data`；
- `GravityCompensator` 使用 `g(q)` 组合不同控制律；
- MuJoCo 层接收控制命令，负责仿真与验证。

## Pimpl：编译防火墙

Pimpl 在头文件中只保留实现的前置声明和指针：

```cpp
class PinModel {
 private:
  struct Impl;
  std::unique_ptr<Impl> impl_;
};
```

具体成员定义在 `.cpp` 中。这样，使用者不需要包含 Pinocchio 的大型头文件，内部成员变化也不会迫使所有调用方重新编译。

Pimpl 的主要价值是：

- 隐藏第三方库和实现细节；
- 减少头文件依赖与重复编译；
- 稳定公开接口和对象布局。

Pimpl 不是运行时优化。它通常会增加一次堆分配和指针间接访问。本项目真正的运行时优化是模型只加载一次，并复用 Pinocchio `Data` 工作区。

## `inline`

`inline` 的语言层含义是：允许同一函数定义出现在多个翻译单元中。因此，定义在头文件里的非模板函数通常需要 `inline`，以避免重复定义错误。

```cpp
inline int twice(int value) {
  return value * 2;
}
```

类内定义的成员函数隐式具有 `inline` 属性：

```cpp
const std::string& model_path() const { return model_path_; }
```

`inline` 不保证编译器把函数调用展开。是否展开由编译器根据优化策略决定；即使没有写 `inline`，编译器也可能展开。

因此：

- Pimpl 倾向于减少头文件暴露，改善编译隔离；
- 头文件内联实现会暴露更多实现，可能增加编译依赖；
- 应按接口稳定性和实际性能测量选择，而不是看到短函数就机械地加 `inline`。
